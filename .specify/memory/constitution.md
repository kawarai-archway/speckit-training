# トレーニングECサイト 憲章

## 基本原則

### I. テンプレート駆動開発

すべての UI・API・テスト実装は `src/templates/` のテンプレートを基に構築する。
共通基盤は `src/foundation/` を使用し、独自の基盤実装を禁止する。

- UI 実装は `@/templates/ui/pages/`（一覧・詳細・フォーム）および
  `@/templates/ui/layouts/`（購入者・管理者レイアウト）を使用しなければならない
- API 実装は `@/templates/api/usecase` および `@/templates/api/handler` を
  使用しなければならない
- リポジトリ実装は `@/templates/infrastructure/repository` の
  `createHmrSafeStore` を使用しなければならない
- テスト実装は `src/samples/tests/` 配下のサンプルテストを参照し、
  同等の構造で作成しなければならない

**根拠**: テンプレートに統一することで実装品質のばらつきを排除し、
学習コストを最小化する。

### II. ドメイン分離

各ドメインは `src/domains/[domain]/` に独立して実装する。
ドメイン間の依存は API 経由のみとし、直接インポートを禁止する。

- 各ドメインは `api/`（ユースケース）と `ui/`（コンポーネント）の
  2 層で構成しなければならない
- ドメイン実装は `src/contracts/` の共有インターフェースに準拠
  しなければならない
- ドメイン間でデータを共有する場合は REST API 経由とし、
  モジュール間の直接インポートを禁止する
- サンプル実装（`src/samples/`）と本番実装（`src/domains/`）の
  依存を禁止する

**根拠**: ドメイン間の結合を排除し、独立したデプロイ・テスト・
開発を可能にする。

### III. テスト駆動開発（TDD）必須（非交渉）

TDD（Red → Green → Refactor → 検証）を徹底する。
本原則は非交渉であり、例外を認めない。

#### Red フェーズ

以下の 4 種別のテストを実装前に作成し、すべて FAIL することを確認する:

1. **ユースケース単体テスト**: ドメインロジックの正常系・異常系・認可条件
2. **UI コンポーネント単体テスト**: 表示・インタラクション・アクセシビリティ
3. **API 統合テスト**: エンドポイントの入力バリデーション・認可・レスポンス形式
4. **E2E テスト**: ユーザー導線の主要フロー

**テスト記述ポリシー（仕様ベーステスト原則）**:

- テストは本来成功すべき正しい仕様（Given-When-Then）に基づいて記述する
- テストが失敗する理由は、実装コードが未実装
  （NotImplementedError 等）であるためとする
- **禁止パターン（一時的 FAIL テスト）**:
  - `expect(true).toBe(false)` 等の意図的失敗アサーション
  - `throw new Error('Not implemented yet')` 等のテストコード内の
    意図的例外
  - `it.todo()` / `it.skip()` による Red 状態の代替
  - 一時的に失敗する実装スタブの作成（Green フェーズで差し替え前提）

#### Green フェーズ

- 失敗するテストを成功させるために必要な最低限のコードを記述する
- テストコードを一切変更せず、実装コードのみを追加してテストを通す
- 全テストがパスすることを検証する

#### Refactor フェーズ

- 重複排除・命名改善・責務分離を実施する
- 全テストが引き続きパスすることを検証する
- 不要と判断した場合はその理由を明記する

#### 検証フェーズ

- E2E テスト実行（証跡付き）+ カバレッジ確認を実施する

#### テスト実行義務（非交渉）

- TDD 各フェーズでテストランナーをシェル実行し、結果を検証することを
  義務化する
- テストファイルを作成しただけではフェーズ完了とみなさない。
  テストランナーによる実行結果で合否を判定する
- テスト実行結果の証跡（パス件数・失敗件数）を記録する義務がある
- 特定のテストランナーやパッケージマネージャーに依存せず、
  プロジェクトのテストインフラを使用する
- **フェーズ別検証基準**:
  - Red: 新規テストが FAIL（未実装エラー）+ 既存テストが PASS
    （リグレッションなし）
  - Green: 全テストが PASS + テスト件数 > 0
  - Refactor: 全テストが PASS
  - 検証: カバレッジ 80% 以上 + E2E テスト PASS

#### 実装ガードレール（非交渉）

- E2E テスト実行の前提条件（ブラウザインストール等）を CI 定義または
  フレームワーク固有パターンから検出し、初回 E2E 実行前に自動実行する
- ユーザーストーリー完了時に全テスト（ユニット・統合・E2E）のパスを
  確認するストーリー完了ゲートを設ける。テスト失敗が残っている場合は
  次のストーリーに進まない
- 標準アーキテクチャの保護対象レイヤー（Foundation, Templates,
  Contracts, Infrastructure、ルート設定ファイル）への改変を禁止する。
  変更許可範囲は Domains, App ルート, Tests に限定する
- フェーズゲート（Red/Green/Refactor）ではユニット・統合テストのみ
  実行し、E2E テストはストーリー完了ゲートでのみ実行する
  （2 層テストゲート）
- Refactor フェーズの対象は当該ストーリーで変更したファイルのみとし、
  既存コードの大規模リファクタリングを禁止する

**根拠**: テスト駆動開発により仕様の正確性を実装前に検証し、
リグレッションを防止する。実行義務により「テストを書いたが動かさない」
という形骸化を排除する。

### IV. 共通 UI コンポーネントの利用

ドメイン実装時は `@/templates/ui/components/` の共通コンポーネントを
使用し、同等機能の独自実装を禁止する。

- ボタン・フォーム・テーブル・モーダル等の基本 UI 部品は
  共通コンポーネントを使用しなければならない
- 共通コンポーネントに存在する機能と同等の独自コンポーネント作成を
  禁止する
- 共通コンポーネントに不足がある場合は、ドメイン固有コンポーネント
  として `src/domains/[domain]/ui/` に配置する

**根拠**: UI の一貫性を保証し、重複実装によるメンテナンスコストを
排除する。

### V. 実装ワークフロー

スタブ置換パターンで本番実装に切り替える。

- **API**: `NotImplementedError` → 本番 API（501 応答が解消）
- **UI**: 「ドメイン未実装」プレースホルダー → 本番コンポーネント
- 既存の本番ページ・API Routes は配置済み
  - 本番ページ: `src/app/(buyer)/`, `src/app/admin/`
  - API Routes: `src/app/api/`
  - `@/domains/` のスタブを置換すれば自動的に動作する
- `src/contracts/` を基盤とし、`src/samples/` を参考に実装する
  - `spec.md` が要求するフィールドが contracts にない場合は拡張する
  - 「モデルにないから」は要件スキップの理由にならない
- **spec.md は実装すべき機能の唯一の情報源である**
  - 定義されていない機能は実装しない（スコープ外は除外）
  - 定義された機能は data-model.md や contracts の不備を理由に
    スキップしない
- ユーザーストーリー単位でフェーズを分割し、各ストーリーを独立して
  実装・テスト可能にする
- ドメイン実装時に navLinks のコメントを解除する
  - 購入者向け: `src/app/(buyer)/layout.tsx`
  - 管理者向け: `src/app/admin/layout.tsx`
  - 実装したドメインのリンクのみ有効化する

**根拠**: スタブ置換パターンにより、既存アーキテクチャを破壊せずに
段階的に本番実装へ移行できる。spec.md を唯一の情報源とすることで
実装範囲の曖昧さを排除する。

## 品質基準

### 静的解析

- **TypeScript**: strict モード、コンパイルエラー 0 件を必須とする
- **ESLint**: エラー 0 件を必須とする

### テストカバレッジ

- テストカバレッジ 80% 以上を必須とする
- 各ユーザーストーリー完了時にプロジェクトのカバレッジコマンドを
  実行し 80% 以上を確認する
- CI での失敗を待たず、ローカルで事前に検証する
- カバレッジが不足する場合は、不足テストを追加してからストーリーを
  完了とする

### E2E テスト

- 主要導線をカバーする E2E テストを必須とする
- 各ユーザーストーリー完了時にプロジェクトの E2E テストコマンドを
  実行し全パスを必須とする
- テスト実行結果の出力を確認し、パス件数 0 件はエラーとする
- 「テストを実行した」と報告するだけでは不十分。実行結果の出力
  （パス/失敗件数）を証跡として提示すること
- 実装のみで実行スキップは不可

### 外部リソース検証

- シードデータに外部 URL（画像等）を含める場合、実装時に各 URL に
  HTTP リクエストを送信し存在を確認する。失敗した URL は代替 URL に
  置換する
- plan 時点では検証予定とし、検証済みとしない
- LLM が生成した URL は実在しない可能性がある

### サンプルコード保護

- 本番実装によるサンプルコード破損を防止する
- contracts の新規フィールドは `.default()` または `.optional()` を
  付与する
- シードデータはベース（不変）と拡張（本番追加分）に分離する
- リポジトリインターフェースの検索パラメータ追加はオプショナルとする

### パフォーマンス

- 一覧ページ初回ロード 3 秒以内を必須とする

### テスト配置規約

- 本番ドメインの単体テストは `tests/unit/domains/[domain]/` に
  配置する
- 本番ドメインの統合テストは `tests/integration/domains/[domain]/` に
  配置する
- 本番 E2E テストは `tests/e2e/` 直下に配置する
- `src/samples/tests/` 配下はサンプル実装専用であり、
  本番ドメインのテストを追加してはならない
- テスト作成時は `src/samples/tests/` 配下のサンプルテストを
  参照すること

### E2E テスト実行時の注意事項

- E2E テスト実行前にポート 3000 を占有している既存プロセスを
  必ず停止する
- Windows 環境では Bash の `$_` が extglob で壊れるため、
  PowerShell スクリプトは `powershell.exe -File -` + heredoc で
  実行する
- データ変更後は `.next` キャッシュを削除してからサーバーを
  再起動する（`globalThis` のインメモリストアが HMR で残るため）

## 実装ワークフロー

### 技術スタック

| カテゴリ | 技術 |
|---------|------|
| フレームワーク | Next.js 14 (App Router) |
| 言語 | TypeScript 5 (strict mode) |
| UI ライブラリ | React 18 |
| CSS | Tailwind CSS 3 |
| バリデーション | Zod |
| 単体・統合テスト | Vitest |
| E2E テスト | Playwright |
| ストレージ | インメモリストア（`globalThis` + `Map<string, T>`） |

### 認証・認可

| 項目 | 仕様 |
|-----|------|
| ロール | buyer（購入者）, admin（管理者） |
| セッション管理 | Cookie-based |
| 認可モデル | RBAC (Role-Based Access Control) |
| ログイン必須 | `requireAuth()` |
| 管理者限定 | `requireRole(request, 'admin')` |
| 購入者限定 | `requireRole(request, 'buyer')` |

### 命名規約

| 対象 | 規約 | 例 |
|-----|------|-----|
| ファイル名 | kebab-case | `product-list.tsx` |
| コンポーネント | PascalCase | `ProductList` |
| 関数 | camelCase | `getProducts` |
| 定数 | UPPER_SNAKE_CASE | `MAX_ITEMS` |
| 型 | PascalCase | `ProductType` |

### プロジェクト構造

```text
src/
  app/                    # 本番ページ・API Routes（@/domains/ 経由）
    (samples)/sample/     # サンプルページ・API Routes（/sample/* URL）
  contracts/              # 共有インターフェース
  domains/                # ドメインスタブ（NotImplementedError）
  foundation/             # 共通基盤（認証・エラー・バリデーション）
  infrastructure/         # リポジトリ実装
  samples/domains/        # サンプルドメイン実装
  samples/tests/          # サンプルテスト（unit/integration/e2e）
  templates/              # UI テンプレート
tests/
  e2e/                    # 本番 E2E テスト
  unit/domains/           # 本番単体テスト
  integration/domains/    # 本番統合テスト
```

## ガバナンス

### 修正手順

1. 修正提案を文書化し、影響範囲を明示する
2. 関連するテンプレート・仕様書への影響を評価する
3. セマンティックバージョニングに基づきバージョンを更新する
4. 依存するテンプレート（plan-template, spec-template, tasks-template）
   との整合性を確認する
5. 同期影響レポートを更新する

### バージョニングポリシー

- **MAJOR**: ガバナンス・原則の後方互換性のない削除または再定義
- **MINOR**: 新規原則・セクションの追加、または既存ガイダンスの
  実質的な拡張
- **PATCH**: 文言の明確化、誤字修正、意味を変えない改善

### コンプライアンス確認

- すべての PR・コードレビューで本憲章への準拠を検証する
- 原則 III（TDD 必須）は非交渉であり、例外を認めない
- 保護対象レイヤー（Foundation, Templates, Contracts, Infrastructure）
  への変更は禁止する
- 実行時の開発ガイダンスは `CLAUDE.md` を参照する

### 言語規約

すべてのプロジェクト憲章・仕様書・計画・タスク・実装に関する
ドキュメントは見出し・本文ともに日本語で記述すること。
